System design v1 · 2026-10-01

FlashDrop

A live-shopping flash-sale platform that sells a limited drop to a burst of buyers without overselling, double-charging or losing an event, and proves it with machine-checked invariants.

This page walks through the design as a flow, from the first page view to a paid order and every way that path can break. It summarises system-design.md, which stays the source of truth.

The core rule

  1. 01

    Redis admits

    A Redis Function, fd_reserve, atomically checks the drop window, the per-user limit and the stock and takes a hold, so losers get a read-only O(1) answer and never touch Postgres.

    fd_reserve · Lua · O(1)

  2. 02

    Postgres decides

    Every winner becomes an orders row in one transaction with its quota, stock counters and outbox row under CHECK constraints, so Postgres arbitrates every reservation's fate and owns every deadline.

    orders · drop_inventory · CHECK

  3. 03

    Kafka carries the news

    Checkout ends at a compare-and-set plus an outbox row, and a relay publishes to orders.v1, keyed by productId, where idempotent consumers run payment, settlement and the live dashboard.

    outbox · orders.v1 · 3 groups

  4. 04

    Timers clean up

    Postgres-driven sweepers expire unpaid orders and return stock even if Kafka loses or poison-pills events, and a reconciler rebuilds Redis from Postgres after a restart or wipe.

    sweeper · safety net · reconciler

02 · Architecture

A modular monolith: four deployables, two images

A pnpm + Turborepo monorepo on PostgreSQL 17, Redis 8 and Kafka 4. Request handling, background loops and Kafka consumers run as separate processes built from the same node image and switched by role flags. One docker compose command starts everything, locally and in GitHub Actions.

Source: §2 Architecture overview

Deployables and their jobs

worker and consumers are one deployable run as two Compose services; the one-shot migrate job uses the same node image.

  • web

    Next.js 16.3 · React 19.3 · Tailwind 4

    Storefront, SSR product pages, live room, checkout, order page and admin UI. No database or Redis credentials: it reads and writes only through api.

  • api-1, api-2

    Node 22 · Fastify 5 · ws

    REST /api/v1 plus the WebSocket gateway at /ws (API_ROLES=http,ws) and rate limiting. Two stateless replicas prove cross-instance pub/sub fan-out.

  • worker

    WORKER_ROLES=relay,sweeper,reconciler,listing

    Outbox relay to Kafka; Postgres-driven expiry, safety net and drop scheduler; Redis reconciler and rebuild; LLM listing jobs. Leader-elected per loop with Postgres advisory locks.

  • consumers ×2

    WORKER_ROLES=payment,settlement,dashboard

    Consumer groups payment, inventory-settlement and sales-dashboard across 6 partitions. Two replicas demonstrate rebalancing when one is killed.

  • payment-mock

    Node 22 · Fastify 5

    A simulated PSP behind a real socket: charges with Idempotency-Key, close-by-reference (refund plus fence), a ledger in the psp schema, and configurable latency, errors, declines and timeout-after-success.

  • caddy

    Caddy 2 · edge on :8080

    / to web; /api/*, /ws and /uploads/* round-robin to api-1/api-2; /ws/1 and /ws/2 pinned for deterministic tests; 404 for /_internal/*.

  • infra

    postgres:17.11 · redis:8.10.2 · apache/kafka:4.3.1

    Single-node data stores, the one-shot kafka-init and migrate jobs, and an optional kafka-ui. Compose Postgres is published on 5433 because a native PostgreSQL 17 owns 5432.

Why this split

  • The WebSocket gateway lives outside Next.js, because Route Handlers can't hold WebSocket upgrades, but inside api behind a role flag: one fewer deployable, and it can still become its own pool with no code change.
  • worker is separate from api so background loops never compete with request latency, and singletons (relay, sweeper, reconciler) stay out of the scaled request tier.
  • One worker image with roles, not microservices. Consumer groups already give independent offsets, failure isolation and scaling.
  • payment-mock runs across a network boundary, the only way to test timeouts, unknown outcomes and the ledger that proves "no double charge".
  • One Postgres with package-level domain boundaries. One developer, one transaction boundary.
Data model: the tables behind the flow

Core tables: users, rooms, products, drops, drop_inventory (the stock of record and the hard oversell backstop), user_drop_quota, orders (a reservation is an order in status RESERVED) and payments. Support tables: outbox, processed_events, sales_minute, drop_sales_totals, listing_jobs, system_state, sweeper_quarantine, and the psp schema (psp.charges, psp.references).

The schema is TypeScript with Drizzle (drizzle-orm 0.45.3, drizzle-kit 0.31.11). Every statement that carries a guarantee stays hand-written SQL through Drizzle's sql template. Global lock order: orders row(s) → user_drop_quota row → drop_inventory row, always last.

  1. Step 1 of 9

    Browse the SSR product page

    Whoweb→callsapi

    The browser opens /p/[slug]. The product shell comes from a 'use cache' helper called at request time (cacheTag('product:' + id)), and a dynamic <Suspense> hole, <LiveStock>, fetches the stock snapshot uncached and streams it in the same response.

    web holds no database or Redis credentials: Server Components call api over API_INTERNAL_URL, forwarding the session cookie. No page fetches api at build time.

    Guarantee

    The raw HTML response contains the title and the current stock number (ssr.spec asserts it on the raw response). SSR embeds {avail, held, gen, seq}, so hydration never goes backwards.

    Read more: §8.1 Routes and rendering

  2. Step 2 of 9

    Live stock over WebSocket

    Whoapi WS gateway←subscribed toRedis pub/sub

    One RealtimeClient per tab opens /ws (same-origin through Caddy) and sends sub for stock:<dropId>. The gateway subscribes to fd:ch:stock:{d:<dropId>} first, then reads HMGET inv and sends a snapshot.

    Every stock Function (fd_reserve, fd_confirm, fd_release, fd_rebuild, fd_set_status) publishes the new level on each mutation. The gateway keeps the latest level per topic and flushes dirty topics every 100 ms as delta frames.

    Guarantee

    The client applies a frame only if its (gen, seq) is newer, so the SSR snapshot and the first frame can't race in either direction. Each socket gets at most 10 stock frames per second.

    Read more: §7 Real-time · §8.2 Live stock client

  3. Step 3 of 9

    Reserve: Redis admits, Postgres decides

    Whoapi→thenRedis fd_reserve→thenPostgres

    Buy creates a uuidv7 Idempotency-Key, kept in sessionStorage per drop, and calls POST /api/v1/drops/:dropId/reservations. The API derives rid = uuidv5(userId:dropId:Idempotency-Key).

    fd_reserve atomically checks the drop window, the per-user limit (uq) and avail, then takes a hold (avail −q, held +q, rsv entry HELD) and publishes the new level. Losers stop there with a 409. Winners run one Postgres transaction, in lock order:

    1. INSERT orders (id = rid, status RESERVED) ON CONFLICT DO NOTHING
    2. claim user_drop_quota under within_limit
    3. INSERT outbox order.reserved
    4. takeStock: UPDATE drop_inventory, last, guarded by redis_gen, stock and the drop window

    Commit, then 201 with orderId, expiresAt and serverNow. If Postgres refuses with SOLD_OUT, LIMIT or NOT_LIVE, the API writes a REJECTED tombstone and its order.rejected event in one statement; a stale generation answers 503 instead, retried with the same key.

    Show the takeStock statement 
    UPDATE drop_inventory di SET reserved = di.reserved + $q, updated_at = now()
FROM drops d
WHERE di.drop_id = $dropId AND d.id = di.drop_id
  AND di.redis_gen = $gen                                  -- generation fence (§4.7)
  AND di.total - di.sold - di.reserved >= $q               -- stock backstop (INV-1)
  AND d.status IN ('SCHEDULED','LIVE') AND now() >= d.starts_at AND now() < d.ends_at
RETURNING di.reserved;
    Guarantee

    No oversell (INV-1) and no user over the limit (INV-3): Lua is the fast gate, the CHECK constraints are the hard backstop. Postgres sees only winners. The same request always maps to the same rsv field and orders.id, so a retry replays with 200 instead of creating a second order.

    Read more: §5.2 Reserve → checkout → outbox · §4.5 Per-user limits and idempotency

  4. Step 4 of 9

    Checkout submit: one CAS, then 202

    Whoapi→thenPostgres

    The checkout form creates its own Idempotency-Key once per order and keeps it in sessionStorage under the order id. POST /api/v1/orders/:orderId/checkout runs one transaction: a CAS from RESERVED to PENDING_PAYMENT (owner only, not expired, expires_at = now() + payment_seconds), an order.placed outbox row and pg_notify('outbox').

    The request ends at the commit with 202 PENDING_PAYMENT, and the UI shows "Processing…". If the CAS loses, the API re-reads: same key and hash → 200 replay, different hash → 422, another key → 409 ALREADY_SUBMITTED, expired → 410.

    Show the checkout CAS 
    UPDATE orders SET status = 'PENDING_PAYMENT', checkout_key = $key, checkout_hash = $hash,
       shipping = $shipping, payment_method = $pm,
       expires_at = now() + make_interval(secs => $paymentSeconds), version = version + 1, updated_at = now()
WHERE id = $orderId AND user_id = $userId AND status = 'RESERVED' AND expires_at > now()
RETURNING *;
    Guarantee

    Checkout never touches Redis or the PSP, so PSP latency and outages never hold HTTP handlers or database connections. With Kafka and payment-mock stopped, submit still returns 202 (the checkout-decoupled test).

    Read more: §5.2 Reserve → checkout → outbox

  5. Step 5 of 9

    Outbox relay

    Whoworker (relay)→publishes toKafka

    The relay wakes on LISTEN outbox (checkout, cancel and expiry batches notify) or on a 250 ms poll. Each batch is one transaction on one connection:

    1. pg_try_advisory_xact_lock(hashtext('fd.relay')), so one publisher at a time
    2. select up to 500 rows WHERE published_at IS NULL ORDER BY id, FOR UPDATE SKIP LOCKED
    3. producer.send with headers event-id, event-type, schema-version, trace-id; resolves on broker acks
    4. mark published_at and commit

    On a send failure it rolls back and backs off (1 s → 30 s, full jitter).

    Guarantee

    No lost events (INV-5). Status polling, not an id cursor, so a late-committing row is never skipped. A crash after send but before the mark republishes the batch, and consumers dedupe.

    Read more: §5.4 Transactional outbox and relay

  6. Step 6 of 9

    Kafka orders.v1, keyed by productId

    WhoKafka 4 (KRaft)

    orders.v1 has 6 partitions and 7-day retention and carries the whole order lifecycle. The producer (@confluentinc/kafka-javascript) runs with enable.idempotence=true, acks=all and partitioner=murmur2_random, so a key lands on the partition a Java producer would choose.

    Envelopes are Zod-validated before the outbox insert and again on consume. Events are "fat" (they carry qty and the ids) and keep shipping addresses out.

    Guarantee

    All events of one order share a partition, so per-order causal order holds end to end, and each product's aggregate has a single writer. The partitioning test asserts partition = murmur2(productId) % 6.

    Read more: §6.1 Topics · §6.2 Event envelope

  7. Step 7 of 9

    Payment consumer charges, then CAS to PAID

    Whoconsumers: payment→callspayment-mock

    On order.placed the handler re-reads the order. If it is PENDING_PAYMENT, it calls POST /v1/charges with Idempotency-Key: charge:<orderId>. On succeeded, one transaction does the CAS to PAID, writes a SUCCEEDED payments row and order.paid, and moves the inventory (reserved −q, sold +q, last). The status is then pushed on fd:ch:user:<userId> to the buyer's order page.

    Batches are grouped by orderId (sequential within an order) with up to 32 orders in flight, so a hot product partition still pays quickly.

    Guarantee

    No double charge (INV-4). A PSP timeout or 5xx pauses the partition and retries the same key, never the DLQ. If the CAS loses to expiry or cancel, close-by-reference refunds the charge.

    Read more: §6.5 Handlers · §6.3 Consumer groups

  8. Step 8 of 9

    Inventory settlement confirms the hold in Redis

    Whoconsumers: inventory-settlement→callsRedis fd_confirm

    On order.paid, settleRedis re-reads the Postgres status, calls fd_confirm (the rsv entry goes HELD → COMMITTED, held −q, sold +q, seq +1, publish) and then sets redis_settled_at. Every viewer sees the new level through the gateways.

    Guarantee

    Redis applies an outcome only after Postgres committed it, so Redis is never optimistic (INV-7) and agrees with Postgres (INV-8). A redelivery is skipped once redis_settled_at is set, and the Lua state machine answers NOOP if it reaches Redis again; a CONFLICT is an INV-8 breach that goes to the DLQ with an alert.

    Read more: §6.5 Handlers · §4.3 The arbiter rule

  9. Step 9 of 9

    Sales dashboard projection and live push

    Whoconsumers: sales-dashboard→publishes throughapi WS gateway

    Per batch, one transaction inserts the event ids into processed_events, folds only the new events into sales_minute (by event-time minute) and drop_sales_totals with version + 1. After the commit and the Kafka offset commit, it publishes fd:ch:dash:<dropId> with {version, totals}; the admin dashboard follows dash:<dropId> and stock:<dropId>.

    Guarantee

    Exactly-once effects for the projection. Totals (not deltas) and a strictly newer version make duplicate and out-of-order publishes harmless. Dashboard totals equal Postgres truth (INV-5), and pnpm dash:rebuild converges to identical numbers.

    Read more: §9 Live sales dashboard

End stateThe order is PAID; the units count as sold in Postgres and Redis; the charge sits in the PSP ledger; the dashboard has counted it. verify:invariants checks exactly this after every load and chaos run.

Side branches and failures

The happy path is the easy part. These are the branches the design is built around; each ends with stock and money back in a consistent state.

  • Timer

    Hold or payment expiry

    expire-orders runs every 1 s as an advisory-lock leader. In one transaction, in lock order, it moves up to 200 due RESERVED or PENDING_PAYMENT rows to EXPIRED, gives back quota and reserved, and writes order.expired. Settlement calls fd_release; the payment group calls close-by-reference, which refunds a charge that raced the expiry and fences later ones. If the event is lost, settle-safety-net settles the order directly.

    OutcomeStock returns, within about 15 s even through the safety net alone; net capture is 0.

    §4.6 Expiry and the safety net

  • Payment

    Payment declined

    The PSP answers declined (for example pm_decline) or reference_closed. The payment consumer's CAS moves PENDING_PAYMENT to PAYMENT_FAILED and, in the same transaction, writes a FAILED payments row, gives back quota and reserved, and emits order.payment_failed. Settlement then releases the Redis hold.

    OutcomeThe units go back on sale and the buyer's quota is returned.

    §6.5 Handlers

  • Buyer

    Cancel

    POST /api/v1/orders/:orderId/cancel is a CAS from RESERVED or PENDING_PAYMENT to CANCELLED, with quota and reserved given back and order.cancelled written in the same transaction. The checkout page's "Leave checkout?" dialog calls it. Settlement releases the hold; the payment group closes the reference.

    OutcomeStock returns through settlement; a charge that raced the cancel is refunded.

    §4.4 State machine

  • Crash

    api crashes between Lua and Postgres

    Redis holds a HELD entry that Postgres never recorded: an orphan. A retry with the same key heals it (EXISTING, no row, so the insert succeeds). Otherwise orphan-scan finds it after expiry + 30 s of grace and writes a REJECTED/ORPHANED tombstone with its order.rejected event in one statement; the primary key decides any race with a late insert. Then the hold is released.

    OutcomeStock is returned late, never lost.

    §4.6 orphan-scan · §4.5

  • Redis

    Redis restart or wipe

    Within 2 s the reconciler sees a changed run_id, a missing fd:epoch or a missing library. It reloads the Functions and, for each tracked drop under the drop lock, sets RECONCILING (reserves get 503 with Retry-After: 1), bumps redis_gen so in-flight reserves fail the generation fence, snapshots Postgres and runs one atomic fd_rebuild.

    OutcomeAbout 1–3 s of 503s per drop. After a wipe, 503s and never wrong answers; after a restart, Redis may be stale for up to 2 s before detection, and the Postgres CHECK covers that window.

    §4.7 Rebuild and reconciliation

  • Kafka

    Kafka is down

    Checkout keeps working because it only writes Postgres. Relay transactions roll back after a send timeout of at most about 10 s, so vacuum isn't blocked; the outbox grows, and an alert fires when the oldest unpublished row is older than 10 s. Payments are delayed; orders past their window expire, and late charges are refunded.

    OutcomeStock returns via the safety net; the 5-minute payment window is the outage budget.

04 · Inventory and reservations

Redis is the gate, Postgres is the arbiter

Stock lives in two places on purpose. Redis turns 10–100× over-demand into microsecond, read-only rejections and hosts the pub/sub fan-out; Postgres holds the stock of record and decides every reservation's fate. With Postgres-only stock, every loser would queue on one row lock.

Source: §4 Inventory & reservations

Postgres decides every reservation's fate. Redis never frees stock on its own clock.

Reserve

Redis takes the stock first, then Postgres records the order. Redis is briefly lower.

Release or commit

Postgres commits the outcome first, then Redis applies it, through the settlement consumer or the safety net. Redis is briefly lower again.

So Redis is never higher than Postgres (INV-7). If Redis is ever wrong, the CHECK and the conditional UPDATE still prevent oversell: the worst case is a buyer admitted by Redis who then gets a 409 from Postgres, an under-sell, never an oversell. The drop window is checked twice as well: Lua admits only inside [startsAt, endsAt) while the status is SCHEDULED or LIVE, and the Postgres stock UPDATE repeats the check against drops.

Redis Functions: library flashdrop

All keys of a drop share the hash tag {d:<dropId>}, so every call touches one slot. Redis does not roll back a Function that errors after a write, so every Function either errors before its first write or does not error at all.

fd_reserve
Validates qty, then checks the drop window, the per-user limit and the stock and takes a hold: avail −q, held +q, uq +q, an rsv entry HELD, an exp entry, then publish. Replays answer EXISTING or FP_MISMATCH.
fd_confirm
HELD → COMMITTED after Postgres says PAID: held −q, sold +q. NOOP if already committed, CONFLICT if released.
fd_release
HELD → RELEASED after a terminal unpaid or REJECTED order: stock and quota come back, and the entry stays as an idempotency tombstone.
fd_rebuild
Atomically replaces a drop's keys from a Postgres snapshot. Validates the whole snapshot before its first write, returns STALE unless its gen is newer, and is the only way out of RECONCILING.
fd_set_status
Writes the drop status. RECONCILING creates a complete fail-closed hash if the keys are gone; any other status is refused with RETRY while the drop is RECONCILING.
fd_rl_hit
A fixed-window counter (INCR, plus PEXPIRE on the first hit) behind the custom node-redis store for @fastify/rate-limit.

Two state machines

Every Postgres transition is a CAS (UPDATE … WHERE status = <expected>) that changes the counters and writes the outbox row in the same transaction. The orders row lock is the single linearization point for every race on one order.

Idempotency, layer by layer

rid = uuidv5(NS, userId + ':' + dropId + ':' + idempotencyKey) gives both layers one identity, so no separate idempotency table is needed. The Idempotency-Key header is required (8–64 characters, [A-Za-z0-9_-]) and scoped to (user, drop).

Timers: the sweeper loops

Expiry is decided by Postgres time on Postgres rows; Redis key TTLs and keyspace notifications are never used. Every loop takes pg_try_advisory_xact_lock per tick, and every loop that iterates drops reads the tracked set from Postgres, never from Redis.

Sweeper loops, their period and what they do
LoopEveryWhat it does
expire-orders1 sExpires up to 200 due orders per batch in one transaction, in lock order. A failing batch falls back to one transaction per order; an order that still fails is quarantined with an alert.
settle-safety-net5 sSettles terminal orders with redis_settled_at IS NULL that changed more than 10 s ago, covering a lost, slow or DLQ'd settlement event.
orphan-scan5 sReads exp entries past expiry + 30 s: no Postgres row → REJECTED/ORPHANED tombstone; live → re-score; terminal → forced settle.
drop-scheduler1 sLevel-triggered: applies due Postgres transitions (SCHEDULED→LIVE, LIVE or PAUSED→ENDED) and repairs the Redis status with fd_set_status.
Redis restart or wipe: the rebuild protocol

syncDropFromPostgres(dropId) is the single code path for arming a drop and for recovering it. It runs under one per-drop Postgres advisory lock, shared by admin actions, the scheduler and the reconciler:

  1. fd_set_status RECONCILING: every Function on the drop now answers RETRY. inv is never deleted, so the guard can't vanish mid-rebuild.
  2. Fence: UPDATE drop_inventory SET redis_gen = redis_gen + 1, commit. A reserve carrying the old gen fails, answers 503 and retries with the same key.
  3. REPEATABLE READ snapshot of the drop, drop_inventory, user_drop_quota and every order of the drop.
  4. One atomic fd_rebuild: avail = total − sold − reserved, held = reserved, sold = sold, uq from claimed; RESERVED or PENDING_PAYMENT → HELD, PAID → COMMITTED, everything else → RELEASED; seq resets to 0.
  5. Unlock.

The reconciler checks every 2 s for keyspace loss (fd:epoch, run_id, the library) and structural problems per tracked drop, and every 10 s for drift on stable samples. The rule: lower Redis promptly on evidence, raise it only when quiescent.

05 · Events and Kafka

One topic, keyed by product

Every status change writes its event into outbox in the same transaction. The relay publishes it; three consumer groups turn it into effects, each of them idempotent.

Source: §6 Kafka

Why key by productId

  1. Per-order order. All events of one order share a partition, so per-order causal order holds end to end.
  2. A single writer per product. One consumer instance owns each product's events, so the dashboard folds a batch into one upsert per drop with no cross-consumer lock contention.
  3. The cost is hot partitions. It is bounded, because Kafka sees only winners (about stock × 3–4 events), and payment parallelizes within the partition. Keying by orderId would balance better but give up point 2.

The numbers

Keying by product puts a whole flash sale on one partition. Serially, 1,000 orders at about 450 ms of PSP latency would take about 7.5 minutes, longer than the payment window. With 32 concurrent orders it takes about 15 s. That is safe because correctness rests on the orders CAS and PSP idempotency, not on processing order; work for the same order stays sequential.

Consumer runner rules

  • Manual offsets. Committed only after every message in the batch has succeeded or been dead-lettered.
  • Start at earliest. All groups set fromBeginning: true, so a brand-new group (every CI run) never skips events; a consumer is healthy only once it has a partition assignment.
  • Transient failures stall, never drop. Postgres or Redis errors, PSP 5xx or timeouts and Lua RETRY pause the partition, seek back and retry with backoff (100 ms → 30 s), indefinitely and never to the DLQ.
  • Poison goes to the DLQ. Zod failures, unknown types and InvariantViolation go to orders.v1.dlq with an alert. A DLQ'd event never leaks stock or money: the sweeper, the safety net and close-by-reference still run.
  • Replay without re-feeding. pnpm dlq:replay runs the handler named in x-consumer directly and never re-produces to orders.v1.

06 · Real-time

Live stock without a firehose

Stock is a level, not a log. The Functions publish on every mutation; gateways coalesce, version and fan out, and a snapshot is always enough to recover.

Source: §7 Real-time

  • Functions PUBLISH. Every stock mutation publishes gen:seq:avail:held:sold:status:ts on fd:ch:stock:{d:<dropId>} inside the same atomic call, so messages are ordered with the mutations.
  • Ref-counted subscriptions. Each gateway holds one subscriber connection: it subscribes a channel for the first local socket and unsubscribes after the last. No sticky sessions are needed.
  • 100 ms coalescing. The gateway keeps latest[topic] and serializes each dirty topic once per tick, so a socket gets at most 10 stock frames per second (k6 gate: ≤ 11).
  • (gen, seq) gating. gen comes from Postgres drop_inventory.redis_gen and survives a wipe; seq restarts at 0 on every rebuild. Gateways and clients keep only strictly newer messages.
  • Snapshot + delta resync. On sub the gateway subscribes first, then sends an HMGET snapshot, and re-snapshots after its own subscriber reconnects. Clients reconnect with jittered backoff (0.5 s → 10 s); after 5 s disconnected they poll the stock endpoint every 3 s.
  • Backpressure. Sends are skipped while bufferedAmount > 256 KB, and the next flush carries the latest level. A socket above 1 MB for 10 s is closed with 1013.

07 · Listing generator (LLM)

Photos in, a validated draft out, a human publishes

An admin uploads 1–4 product photos. A worker job asks the model for a structured listing, validates it with Zod, repairs it if needed and leaves publishing to a human. It is a job queue, not a Kafka stream, and it is never on the purchase path.

Source: §10 LLM listing generator

  • Model: claude-sonnet-5-5. The default (owner decision, 2026-10-01), set by LISTING_MODEL. claude-haiku-4-5 is the cheap mode (no effort) and claude-opus-5-5 is for hard cases. On Sonnet and Opus, effort is set explicitly, starting at low.
  • ListingWire vs ListingDraft. Wire is the shape the model must emit: shapes, enums and nullability that constrained decoding can enforce. Draft adds what it can't: title 10–80 characters, description 80–1,200, 3–6 highlights, banned claims, no prices in text, attributes required per category.
  • messages.create(), not parse(). parse() throws on invalid output and hides stop_reason and usage, so the code branches on stop_reason first, then parses inside a try.
  • Repair loop, at most 3 model calls. refusal → FAILED; max_tokens → one retry at effort low, or NEEDS_REVIEW; invalid → a repair turn with z.prettifyError issues; ok → READY; after 3 calls → NEEDS_REVIEW.
  • Fixtures in CI, no key. FixtureListingModel replays Message-shaped fixtures keyed by image sha256: an over-long title, a refusal, max_tokens, invalid JSON and a prompt-injection photo. LLM_PROVIDER defaults to fixture when ANTHROPIC_API_KEY is unset.
  • Human approval. Nothing is published without it. Approve re-validates with ListingDraft and creates a PUBLISHED product with source = 'llm'.
  • The price never comes from the LLM. The admin types it on the drop, which caps what a prompt injection can do; text inside images is data, never instructions.

08 · Correctness

Nine invariants, checked by machine

pnpm verify:invariants waits for quiescence, then checks INV-1 to INV-9 across Postgres, Redis, the PSP ledger and Kafka. It runs after the k6 load-smoke run and the nightly chaos runs, and it is a hard CI gate. The integration suites assert the same checks per test drop.

Source: §1.1 Invariants

  • INV-1

    No oversell.

    reserved + sold <= total for every drop, and Σqty(PAID) ≤ total.

    drop_inventory CHECK (hard), Lua gate (fast)

  • INV-2

    Counters match orders.

    reserved = Σqty(RESERVED, PENDING_PAYMENT) and sold = Σqty(PAID).

    Every status change updates the counters in the same transaction

  • INV-3

    Per-user limit.

    claimed = Σqty(user's RESERVED, PENDING_PAYMENT, PAID) <= limit_qty.

    user_drop_quota CHECK (hard), uq hash in Lua (fast)

  • INV-4

    No double charge.

    For each order, PSP net captured = total_cents if PAID, else 0. At most one succeeded charge per reference. Every PAID order has a SUCCEEDED payments row.

    PSP idempotency keys, orders CAS, close-by-reference

  • INV-5

    No lost events.

    Once idle, the outbox is fully published and every consumer group has processed every event, so dashboard totals equal Postgres truth.

    Transactional outbox, status-polling relay, consumer dedupe

  • INV-6

    No leaked stock.

    Once idle: no live order is past expires_at; every terminal order has redis_settled_at; Redis avail = total − sold − reserved, held = reserved, sold = sold; uq equals claimed.

    Postgres sweeper, settlement consumer, safety net, reconciler

  • INV-7

    Redis is never optimistic.

    Redis avail ≤ Postgres available (total − sold − reserved), except while a drop is RECONCILING or in the detection window after a Redis restart (≤ 2 s plus the rebuild).

    Ordering rule (§4.3), reconciler

  • INV-8

    Redis agrees with Postgres.

    An rsv entry is COMMITTED exactly when its order is PAID. RELEASED implies the order is terminal and unpaid, or REJECTED.

    Settlement reads Postgres status before acting

  • INV-9

    Redis conservation.

    avail + held + sold = total and avail >= 0.

    Lua Functions, model-based tests

What breaks, and what happens

A condensed selection from the failure table. Each row is a deliberate trade-off that holds up in an interview.

  • 50k reserve requests for 500 units

    Lua admits exactly 500. Losers get 409 after one read-only O(1) call. Postgres sees only the winners.

    Why it's fine
    Contention is bounded by stock, not traffic.

  • Postgres refuses what Redis admitted (drift)

    A REJECTED tombstone and its event in one statement → settlement releases → fd_sync nudge → prompt rebuild.

    Why it's fine
    Postgres is the backstop, so oversell is impossible.

  • Redis down

    Reserve answers 503 (fail closed). Checkout submit and payments continue on Postgres; settlement pauses and retries; live updates switch to polling.

    Why it's fine
    No sales beats wrong sales.

  • Postgres down

    The breaker answers 503 before Lua, so no new orphans. Checkout and payments stall; existing holds resolve when Postgres returns.

    Why it's fine
    Fails closed.

  • Payment succeeds just as the order expires

    The orders CAS decides. The loser calls close-by-reference → refund → net capture 0.

    Why it's fine
    One linearization point.

  • PSP timeout (unknown outcome)

    Retry with the same charge: key, indefinitely, with the partition paused; never DLQ'd.

    Why it's fine
    No double charge, no false failure.

  • Poison event

    DLQ + alert. The order still expires and its stock returns through Postgres-driven paths. The replay tool runs only the failing group's handler.

    Why it's fine
    No silent loss, no stuck partition, no double count elsewhere.

  • Kafka data volume lost (RF 1)

    Acknowledged events already marked published are gone. Expiry, the safety net and the PSP ledger still prevent stock or money loss; the dashboard undercounts and INV-5 flags it.

    Why it's fine
    The single-broker limit of "no lost events", stated honestly. Production would use RF 3.

The design takes the correctness core of one proposal, fits it into the delivery footprint of another, and borrows the real-time, accessibility and LLM details of the third.

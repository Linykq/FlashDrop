# M0 spikes: Redis Functions, Kafka client, Next 16 cache APIs, Drizzle

Run on 2026-10-02 against a throwaway Compose project (`fdspike`: `postgres:17.11` on 15433, `redis:8.10.2` on 16379, `apache/kafka:4.3.1` with the §15 single-node settings on 29092). Node 22.14 on Windows 11 for everything except one Linux check in `node:22-bookworm-slim` (Node 22.23.3). Exact package versions: `redis` 6.3.0, `@confluentinc/kafka-javascript` 1.10.1 (librdkafka 2.15.1), `next` 16.3.8, `react`/`react-dom` 19.3.0, `drizzle-orm` 0.45.3, `drizzle-kit` 0.31.11, `pg` 8.23.1, `typescript` 6.0.3, `tsx` 4.23.15.

Everything below was observed by running a script, unless it is marked **(source)** (read from the package's code or type definitions) or **(docs)** (read from the docs bundled in `next/dist/docs`). The spike scripts lived in the session scratch directory and are not part of the repo; the snippets here are the parts that matter, copied from code that ran.

## Design deltas

Things the implementation must do differently from, or more precisely than, the current design text:

1. **`app/_internal/` is a private folder in the App Router and is never routed.** The revalidation handler must live at `apps/web/app/%5Finternal/revalidate/route.ts` to be served at `/_internal/revalidate` (§8.1, §14). See [3.4](#34-revalidation-route-handler).
2. **Next 16.3 adds `io()` (`next/cache`)**, which its docs recommend over `connection()` under Cache Components. Both keep `next build` free of `api` calls (verified); `io()` also allows client prefetch of the cached part (docs). Recommendation in [3.9](#39-recommendation).
3. **Kafka "healthy = assigned" must track the owned partition set.** Under cooperative-sticky, `rebalance_cb` fires `ERR__ASSIGN_PARTITIONS` with an **empty** list for members that gain nothing, so "received an assign callback" is not "has partitions". See [2.5](#25-rebalances-and-healthy--assigned).
4. **Out-of-order completion needs an explicit `seek`.** `resolveOffset()` stores only the highest offset; if message N fails while N+1..M succeed and N+1..M are resolved, N is never redelivered. The runner must resolve only the highest *contiguous* offset, and on a transient failure `pause()` and `seek()` to the first unfinished offset. The deferred `resume()` must sit on a per-partition timer that is cleared on revoke and before `disconnect()`: a `resume()` that fired after disconnect threw, uncaught, and killed the process. See [2.4](#24-eachbatch-manual-commits-and-transient-failures).
5. **The slowest in-flight batch gates the whole member, whatever `partitionsConsumedConcurrently` is.** In 1.10.1, while any batch is in flight the member fetches nothing new, and `pause`/`resume`/`seek` and rebalances wait until it returns (verified at concurrency 1 and 3). Concurrency only runs batches from the same fetch in parallel. So every batch's wall time must be bounded: hard PSP timeouts, and a per-batch deadline after which the runner starts no new work, resolves the contiguous prefix and returns. Backoff is `pause()` + return (as §6.4 says), never a sleep inside the handler. §6.4's "the main loop keeps polling" holds only while batches stay short. See [2.6](#26-a-slow-batch-gates-the-whole-member).
6. **`transaction_timeout` is FATAL, and `pg` then emits `'error'` on the checked-out client.** Without a per-client listener (`pool.on('connect', c => c.on('error', ...))`) this crashes the process. Every pool (api, relay, sweeper) needs it. See [4.6](#46-pool-session-settings-and-connection-killing-errors).
7. **Drizzle's `db.transaction` replaces a connection-killing error with its own failed `ROLLBACK`.** The `25P04` FATAL from `transaction_timeout` reaches the callback, but `db.transaction` then throws `Failed query: rollback` (cause `Connection terminated unexpectedly` or `... not queryable`), with no SQLSTATE. `packages/db` wraps `db.transaction` to rethrow the callback's first error, and the transient-error classifier covers FATAL SQLSTATEs and `pg`'s code-less connection errors. See [4.6](#46-pool-session-settings-and-connection-killing-errors).
8. **`orders_guard` must ignore stored generated columns.** In a `BEFORE UPDATE` trigger, `NEW.total_cents` is `NULL`, so a whole-row "terminal rows are immutable" comparison rejects every update. See [4.3](#43-custom-migration-orders_guard).
9. **The Drizzle migrator never re-checks applied files and (source) only applies migrations newer than the last applied one.** Editing an applied migration is silently ignored (verified). A migration generated on a parallel branch with an older timestamp would be skipped (source). One owner generates migrations, in order.
10. **Raw `db.execute()` through Drizzle's node-postgres driver returns `timestamptz` as a string**, not a `Date` (plain `pg` returns `Date`). `bigint` and `numeric` are strings in both. Hand-written SQL must map its rows explicitly. See [4.5](#45-type-mapping).
11. **A bare JS array in Drizzle's `sql` template expands to `($1, $2, $3)`.** `= ANY(...)` needs `sql.param(ids)`.
12. **node-redis 6 defaults to RESP3** and, by default, holds commands issued while Redis is down until it reconnects (a `PING` stayed pending through the outage). The API hot path should use `disableOfflineQueue: true` (fails fast with `ClientOfflineError`, so the API can answer 503). See [1.5](#15-pubsub-reconnects-and-offline-behaviour).
13. **`apps/web` must not validate runtime env at module scope.** `next build` evaluates route handler modules to collect their configuration; a module-scope `REVALIDATE_SECRET` check failed the build (`Failed to collect configuration for /_internal/revalidate`) when the variable was absent. An image build or the CI `static` job should not need runtime secrets, so read them lazily, at request time. See [3.4](#34-revalidation-route-handler).

The repo's `compose.yaml` already sets `KAFKA_LOG_DIRS` to the `kafka-data` volume; without it the env-configured image writes partitions to `/tmp/kafka-logs` inside the container (observed), which a container re-create would lose.

## 1. node-redis 6.3: Redis Functions, pub/sub, reconnects

### 1.1 Verified facts

| Question | Result |
|---|---|
| Load a library | `client.functionLoad(code, { REPLACE: true })` resolves to the library name (`'flashdrop'`). Without `REPLACE` on an existing library: `SimpleError: ERR Library 'fdspike' already exists`. |
| Typed helpers in the package | Yes: the `functions` client option. Each function is `{ NUMBER_OF_KEYS, IS_READ_ONLY?, parseCommand(parser, ...args), transformReply }`; node-redis sends `FCALL <name> <NUMBER_OF_KEYS>` (or `FCALL_RO` when `IS_READ_ONLY`) and exposes it as `client.<library>.<function>(...args)`. `tsc` enforces the argument list and infers the return type from `transformReply` (a missing argument and a wrong result type were both compile errors). |
| Untyped calls | `client.fCall(name, { keys, arguments })` and `client.fCallRo(...)`; both return `ReplyUnion`. |
| After `FUNCTION FLUSH` | `FCALL` and `FCALL_RO` reject with `SimpleError` (a subclass of the exported `ErrorReply`) whose message is exactly `ERR Function not found`. The function did not run (the hash was unchanged), so one reload-and-retry is safe for write functions. |
| Detect a missing library | `client.functionList({ LIBRARYNAME: 'flashdrop' })` returns `[]` after a flush, one entry after a load. With RESP3 the entries are plain objects `{ library_name, engine, functions: [{ name, description, flags: [] }] }`. |
| `FCALL_RO` | Requires the function to be registered with `flags = {'no-writes'}`; otherwise `ERR Can not execute a script with write flag using *_ro command.` The design's library registers no flags, so it is called with `FCALL` only. |
| Wrong key count | Not detected by Redis: calling a 1-key function with 0 keys ran it with `KEYS[1] = nil` and failed only when `redis.call` got the nil (`ERR Lua redis lib command arguments must be strings or integers`). `NUMBER_OF_KEYS` in one typed definition is the guard. |
| Reply mapping (RESP3 default and RESP2 identical) | Lua array → JS array; Lua string → `string`; Lua integer → `number`; Lua `false` (including a missing `HMGET` field) → `null`; Lua `true` → `1`; `return 'OK'` → `'OK'`. So `fd_reserve`'s `gen` arrives as a string (`["RESERVED","1"]`) and `fd_rl_hit` as numbers (`[1,1000]`). |
| Container restart (`appendonly yes`) | The library and data survive `docker restart`; `INFO server` `run_id` changes. |
| The design's §4.2 library | Loads verbatim on Redis 8.10.2. Walk-through: `fd_set_status LIVE` on a fresh drop → `NO_DROP`; `RECONCILING` → `OK`; `fd_reserve` while reconciling → `["RETRY"]`; `fd_rebuild` → `OK`, again with the same gen → `STALE`; reserve → `["RESERVED","1"]`; replay → `["EXISTING","HELD","1"]`; other fingerprint → `["FP_MISMATCH"]`; over the limit → `["LIMIT"]`; not enough stock → `["SOLD_OUT"]`; `fd_confirm` → `OK` then `NOOP`; `fd_release` of a committed rid → `CONFLICT`; qty 0 → `["BAD_QTY"]`; `fd_rl_hit` → `[1,1000]`. |

### 1.2 Typed library definition (ran under `tsc --strict`)

```ts
import { type CommandParser, createClient, ErrorReply, type RedisFunctions } from 'redis';

const keysFor = (dropId: string) => ({ inv: `fd:{d:${dropId}}:inv`, rsv: `fd:{d:${dropId}}:rsv` });

type ReserveResult = { kind: 'RESERVED'; gen: number } | { kind: 'NO_DROP' | 'SOLD_OUT' | 'BAD_QTY' };

function parseReserve(reply: unknown): ReserveResult {
  if (!Array.isArray(reply) || typeof reply[0] !== 'string') throw new TypeError(`bad reply ${JSON.stringify(reply)}`);
  const [code, gen] = reply;
  if (code === 'RESERVED') return { kind: code, gen: Number(gen) };
  if (code === 'NO_DROP' || code === 'SOLD_OUT' || code === 'BAD_QTY') return { kind: code };
  throw new TypeError(`unknown code ${code}`);
}

type StockSnapshot = { avail: number; gen: number; seq: number; status: string | null } | null;

function parseStock(reply: unknown): StockSnapshot {
  if (!Array.isArray(reply)) throw new TypeError('bad reply');
  const [avail, gen, seq, status] = reply as Array<string | null>;
  if (avail == null || gen == null || seq == null) return null; // HMGET on a missing hash: all null
  return { avail: Number(avail), gen: Number(gen), seq: Number(seq), status: status ?? null };
}

const fdspike = {
  sp_reserve: {
    NUMBER_OF_KEYS: 2,
    parseCommand(parser: CommandParser, dropId: string, rid: string, qty: number) {
      const k = keysFor(dropId);
      parser.pushKeys([k.inv, k.rsv]);
      parser.push(dropId, rid, String(qty));
    },
    transformReply: parseReserve,
  },
  sp_stock: {
    NUMBER_OF_KEYS: 1,
    IS_READ_ONLY: true, // FCALL_RO; the Lua side must register flags = {'no-writes'}
    parseCommand(parser: CommandParser, dropId: string) {
      parser.pushKey(keysFor(dropId).inv);
    },
    transformReply: parseStock,
  },
} as const satisfies RedisFunctions[string];

const client = createClient({ url, functions: { fdspike } });
const r = await client.fdspike.sp_reserve(dropId, 'rid-1', 2); // r: ReserveResult
```

### 1.3 Reload on `ERR Function not found`

```ts
const isFunctionNotFound = (err: unknown): boolean =>
  err instanceof ErrorReply && err.message.startsWith('ERR Function not found');

// On a fresh or flushed Redis the FCALL fails before running anything, so one retry after the load is safe.
async function withLibrary<T>(call: () => Promise<T>): Promise<T> {
  try {
    return await call();
  } catch (err) {
    if (!isFunctionNotFound(err)) throw err;
    await client.functionLoad(LIBRARY, { REPLACE: true });
    return call();
  }
}
```

### 1.4 Pub/sub on a dedicated client

```ts
const cmd = createClient({ url, name: 'api-cmd' });
const sub = cmd.duplicate({ name: 'api-sub' });
for (const c of [cmd, sub]) c.on('error', (err) => log.warn({ err }, 'redis')); // mandatory, see gotchas
await Promise.all([cmd.connect(), sub.connect()]);
await sub.subscribe(channel, (message: string, ch: string) => onMessage(ch, message));
await sub.unsubscribe(channel, listener); // removes this listener only
```

- Two listeners on one channel: `PUBSUB NUMSUB` = 1. After removing one listener the subscription stays (`NUMSUB` still 1) and the other listener keeps receiving. So node-redis keeps the Redis subscription while any listener remains; the gateway's own per-channel count (§7) must remove exactly the listener it added.
- A RESP3 client in subscribed state still runs ordinary commands (`sub.hGet(...)` returned `null`). A dedicated subscriber is still the right call: it keeps push traffic off the command connection.

### 1.5 Pub/sub reconnects and offline behaviour

Event timeline (ms since start) from one run:

```
269 sub: error SocketClosedUnexpectedlyError   <- CLIENT KILL TYPE pubsub
269 sub: reconnecting
269 sub: connect
270 sub: ready                                  <- a PUBLISH sent from this handler was received
...
1118 docker: redis stopped
1307 sub/cmd: reconnecting, error ECONNREFUSED  (repeats with backoff)
2725 docker: redis started
2786 sub: connect, ready                        <- resubscribed (NUMSUB 1), next PUBLISH delivered
```

- **Resubscription completes before `'ready'`.** The socket initiator awaits the resubscribe before emitting `'ready'` (source), and a `PUBLISH` issued from inside the `'ready'` handler was delivered. So "re-snapshot every held topic on `'ready'`" (§7 step 3) is race-free. `'ready'` also fires on the first connect.
- Default reconnect strategy: `min(2^retries × 50, 2000)` ms plus 0–200 ms jitter, retried forever; no reconnect on `SocketTimeoutError` (source).
- **In-flight command when the socket dies:** rejected with `SocketClosedUnexpectedlyError`. The command may or may not have executed; for `fd_reserve` that is exactly the "retry with the same key" case.
- **Default offline queue:** a command issued while disconnected waits; a `PING` sent while Redis was stopped was still pending after 1 s and resolved with `PONG` after recovery.
- **`disableOfflineQueue: true`:** the same `PING` rejected immediately with `ClientOfflineError` (`isReady: false`, `isOpen: true`).
- `client.close()` replaces `quit()`, and `destroy()` replaces `disconnect()` (source: `@deprecated` tags in the typings). There is also a `'terminated'` event, emitted only when the reconnect strategy gives up.

### 1.6 Gotchas

- An `'error'` listener on every client is mandatory: a dropped socket emits `'error'` and, without a listener, crashes the process.
- `events.once(client, 'ready')` **rejects** when the client emits `'error'`, which a reconnecting client always does. Wait with `new Promise((r) => client.once('ready', r))`.
- `keyPrefix` exists in node-redis 6 and prefixes keys pushed with `pushKey`, but not pub/sub channels (source). Do not use it: the Lua code builds the stock channel name itself.

### 1.7 Recommendation

- `packages/inventory` exports one `flashdrop` definition object (shape of 1.2) whose `transformReply`s parse with Zod schemas from `packages/contracts`, so every Lua reply is validated at the boundary. Keys are built only inside `parseCommand` from the drop id, so the key count can't drift.
- All calls go through `withLibrary()`. The reconciler's 2 s check uses `functionList({ LIBRARYNAME: 'flashdrop' })`.
- Two clients per process: a command client with `disableOfflineQueue: true` for request paths (map `ClientOfflineError` and `SocketClosedUnexpectedlyError` to 503 `RETRY`), and a `duplicate()` subscriber that re-snapshots on every `'ready'` after the first.

## 2. @confluentinc/kafka-javascript 1.10.1 (KafkaJS-compatible API)

`import { KafkaJS } from '@confluentinc/kafka-javascript'` works in Node 22 ESM and under `tsx` (the CommonJS named export is detected). `KafkaJS.Kafka`, `KafkaJS.PartitionAssigners`, `KafkaJS.CompressionTypes`, `KafkaJS.ErrorCodes` and `KafkaJS.logLevel` are all available.

### 2.2 Producer

```ts
const kafka = new KafkaJS.Kafka({ kafkaJS: { brokers: ['127.0.0.1:9092'], clientId: 'relay', logLevel: KafkaJS.logLevel.WARN } });

const producer = kafka.producer({
```

Keys inside `kafkaJS` are translated by the compat layer; keys outside it are raw librdkafka properties and win over the translated ones (source: `Object.assign(compatibleConfig, userConfig)`).

| Check | Result |
|---|---|
| Idempotence and lz4 on the wire | `kafka-dump-log.sh` shows `producerId` ≠ -1 with sequence numbers on every batch, and `compresscodec: lz4` on multi-record batches (a 1-record batch was stored uncompressed). |
| `idempotent: true, acks: 1` | Rejected: ``KafkaJSError: `acks` must be set to `all` when `enable.idempotence` is true``. |
| Partitioner | With `partitioner: 'murmur2_random'` all 42 test keys landed where Java's `Utils.murmur2` puts them (`prod-A` → 3, `prod-B` → 2 of 6). **The compat layer forces `murmur2_random` whenever any `kafkaJS` block exists, including the one on `new Kafka(...)`**; only a pure librdkafka config (no `kafkaJS` block anywhere) uses librdkafka's default `consistent_random` (`prod-A` → 5, `prod-B` → 1). Setting it explicitly is still the robust choice. |
| `send()` result | One `RecordMetadata` per partition touched, not per message (12 messages → 4 entries). The `partitioning` test should send one message per call or consume the messages back. |
| Latency | One awaited single-message `send` took 13–14 ms locally with `linger.ms: 5`. |
| Broker unreachable (container paused), `message.timeout.ms: 3000` | `send` rejected after 3.02–3.03 s with `KafkaJSError`, `code: -192` (`ERR__MSG_TIMED_OUT`), `message: 'Local: Message timed out'`, `retriable: false`. |
| Shutdown | `await producer.flush({ timeout: 5000 }); await producer.disconnect();` |

A Java-compatible partition function for the `partitioning` test (verified against the producer for 42 keys):

```ts
export function murmur2(data: Buffer): number {
  const m = 0x5bd1e995;
  const len = data.length;
  let h = 0x9747b28c ^ len;
  const at = (i: number) => data[i] ?? 0;
  for (let i = 0; i + 4 <= len; i += 4) {
    let k = at(i) | (at(i + 1) << 8) | (at(i + 2) << 16) | (at(i + 3) << 24);
    k = Math.imul(k, m);
    k ^= k >>> 24;
    k = Math.imul(k, m);
    h = Math.imul(h, m) ^ k;
  }
  const tail = len & ~3;
  const rest = len % 4;
  if (rest === 3) h ^= at(tail + 2) << 16;
  if (rest >= 2) h ^= at(tail + 1) << 8;
  if (rest >= 1) {
    h ^= at(tail);
    h = Math.imul(h, m);
  }
  h ^= h >>> 13;
  h = Math.imul(h, m);
  h ^= h >>> 15;
  return h;
}
export const javaPartition = (key: string, partitions: number) => (murmur2(Buffer.from(key)) & 0x7fffffff) % partitions;
```

### 2.3 Consumer config

```ts
const owned = new Set<number>();
const consumer = kafka.consumer({
  kafkaJS: {
    groupId: 'payment',
    fromBeginning: true,                  // auto.offset.reset=earliest for a group without committed offsets
    autoCommit: false,
    partitionAssigners: [KafkaJS.PartitionAssigners.cooperativeSticky],
  },
  'js.consumer.max.batch.size': 32,       // the default; eachBatch never exceeded it
  rebalance_cb: (err: KafkaJS.LibrdKafkaError, assignment: KafkaJS.TopicPartition[]) => {
    if (err.code === KafkaJS.ErrorCodes.ERR__ASSIGN_PARTITIONS) for (const p of assignment) owned.add(p.partition);
    else for (const p of assignment) owned.delete(p.partition); // ERR__REVOKE_PARTITIONS
  },
});
await consumer.connect();
await consumer.subscribe({ topics: ['orders.v1'] });
await consumer.run({ eachBatchAutoResolve: false, partitionsConsumedConcurrently: 3, eachBatch });
```

- `fromBeginning: true` on a new group: 30 of 30 messages produced before the group existed were consumed. `fromBeginning: false`: 0 of 30, and only a message produced after the assignment arrived.
- The callback above returns nothing, so the library performs the incremental assign/unassign itself (source). `consumer.rebalanceProtocol()` returned `'COOPERATIVE'` but is missing from the `.d.ts`.
- `consumer.on(...)` is not implemented (source: `notImplemented()`); there are no KafkaJS instrumentation events. `rebalance_cb` is the only rebalance signal.
- The first group on a freshly started broker took 3.0 s to its first assignment; later groups took about 70 ms.

### 2.4 eachBatch, manual commits and transient failures

The batch loop below ran on 100 messages on one partition with a transient failure on message 37, scheduling the resume with a plain `setTimeout(resume, backoffMs)`. The timer bookkeeping around it (`resumeLater`, `cancelBackoff`) is what the shutdown check after the results verified:

```ts
const backoff = new Map<number, NodeJS.Timeout>(); // at most one pending resume per partition

function resumeLater(partition: number, resume: () => void, ms: number): void {
  clearTimeout(backoff.get(partition));
  backoff.set(partition, setTimeout(() => {
    backoff.delete(partition);
    try {
      resume();
    } catch (err) {
      log.debug({ err, partition }, 'deferred resume skipped'); // ERR__STATE: the consumer disconnected meanwhile
    }
  }, ms));
}

function cancelBackoff(partitions: Iterable<number>): void {
  for (const p of partitions) {
    clearTimeout(backoff.get(p));
    backoff.delete(p);
  }
}
// rebalance_cb on ERR__REVOKE_PARTITIONS: cancelBackoff(assignment.map((tp) => tp.partition))
// shutdown: cancelBackoff([...backoff.keys()]); await consumer.disconnect();

eachBatch: async ({ batch, resolveOffset, pause }) => {
  let lastDone: string | undefined;
  for (const m of batch.messages) {
    if (isTransientFailure(m)) {
      resumeLater(batch.partition, pause(), backoffMs); // pause() pauses this partition only and returns its resume
      break;                                            // the library seeks back to the first unresolved offset
    }
    lastDone = m.offset;
    resolveOffset(m.offset);
  }
  if (lastDone !== undefined) {
    await consumer.commitOffsets([{ topic: batch.topic, partition: batch.partition, offset: String(Number(lastDone) + 1) }]);
  }
},
```

Observed: all 100 messages processed; only message 37 was delivered twice, and it was the first delivery after the 1.5 s resume; 5 messages on another partition were processed while this one was paused; the committed offset ended at last + 1. Batch sizes ranged from 1 to 32.

**A pending resume at shutdown.** A partition was paused with a 1.5 s backoff, then the consumer disconnected:

| Backoff handling | Result |
|---|---|
| `setTimeout(resume, 1500)` | The timer fired after `disconnect()`; `resume()` threw `KafkaJSError: Resume can only be called while connected.` (`ERR__STATE`, -172), uncaught: the process exited with code 1. (source: the function `pause()` returns is `() => this.resume(toppars)`, and `resume()` throws unless the consumer is connected.) |
| `resume()` inside `try`/`catch` | The error was caught; the process kept running and exited 0. |
| Timers cleared before `disconnect()` | No resume ran; exit 0. |
| Timers cleared in `rebalance_cb` on revoke | `disconnect()` revoked the partition first, which cleared the timer; exit 0. |

**Out-of-order completion** (message 3 of 0..9 fails, 4..9 succeed and are resolved, as in-batch concurrency would do):

| After the failure | Deliveries |
|---|---|
| `pause()` + `consumer.seek({ topic, partition, offset: failedOffset })` | `0..9, 3..9`: message 3 redelivered |
| `pause()` only, highest offset resolved | `0..9`: **message 3 never redelivered** |

`resolveOffset` stores the highest offset only (source: lower values are ignored), and without an explicit seek the library's automatic seek-back starts after that offset. Hence design delta 4.

### 2.5 Rebalances and "healthy = assigned"

Two members, cooperative-sticky, 6 partitions, continuous production; A was inside a 4 s batch when B joined:

```
  135 A assign [0,1,2,3,4,5]  owns 6
 1708 A slow batch on p0 starts (4 s)
 1770 B start
 3204 B assign []             owns 0   <- empty assign callback
 5719 A slow batch ends, isStale=false
 5720 A revoke [0,1,2]        owns 3   <- the revoke waited for the batch
 6283 B assign [2,1,0]        owns 3
12313 B disconnect
12314 B revoke [0,1,2]        owns 0
12380 A assign [2,1,0]        owns 6   <- 65 ms after B left
16390 A disconnect -> A revoke [0..5]
```

- A's revoke came 1 ms after its slow batch ended, so B waited about 4.5 s for its partitions. This run used the default `partitionsConsumedConcurrently: 1`, but the wait does not depend on it (2.6). The slow batch's `isStale()` stayed `false` and its commit succeeded.
- No message was processed twice across the whole run (1,260 messages, 0 duplicates).
- `disconnect()` revokes every owned partition through the same callback, and the survivor picked them up in about 65 ms.
- With `partitionsConsumedConcurrently: 3` and 30 messages preloaded on 3 partitions (one fetch), up to 3 batches of different partitions were in flight at once (max in flight 3, wall time 947 ms vs 1,569 ms serial). That is parallelism within one fetch only; it does not let other partitions move past a slow batch (2.6).

### 2.6 A slow batch gates the whole member

One member, 6 partitions, continuous production (one message per partition every 20 ms), cooperative-sticky. A 4 s batch on p0; 1 s into it, `consumer.seek()` on p5 to offset 0; later, a second member B joins during another 4 s batch on p0. Same script at both concurrency settings:

| | `partitionsConsumedConcurrently: 1` | `partitionsConsumedConcurrently: 3` |
|---|---|---|
| Batches per other partition in 4 s without a slow batch | 85 | 86 |
| Batches per other partition during the 4 s slow batch | 0 or 1, all started in the same millisecond as the slow batch, none later | 1, all started in the same millisecond as the slow batch, none later |
| `seek(p5)` issued 1 s into the slow batch took effect | 18 ms after the slow batch ended | 48 ms after the slow batch ended |
| B joins during a slow batch: A's revoke | in the same millisecond the slow batch ended (4.0 s after B joined) | in the same millisecond the slow batch ended (4.0 s after B joined) |
| B owns partitions | 2.9 s after the revoke | 2.7 s after the revoke |

So, at both settings, the other partitions got only the batches already in the cache, then nothing until p0 returned; the seek and the rebalance both waited for it.

(source) Why: `#consumeCachedN` calls librdkafka's `consume()` only when no partition's cache is checked out by a worker (`messageCache.assignedSize === 0`); otherwise idle workers wait on `availablePartitions()`. `pause`, `resume`, `seek`, a revoke and cache expiry all go through `#addPendingOperation`, which resolves `#workerTerminationScheduled`: every worker finishes its current batch, then the operations run. Rebalance callbacks are only served inside `consume()`. Each `kafka.consumer()` has its own loop, so the gate is per consumer instance: one group's slow batch does not stall another group's consumer in the same process.

**Bounding a batch by a deadline** (3 partitions, 60 preloaded messages, 200 ms per message, concurrency 3, `eachBatchAutoResolve: false`): the handler started no new message once 1 s had passed, resolved what had finished and returned. The library sought back to the first unresolved offset by itself. All 60 messages were processed, none twice, in 14 batches; the longest batch took 1,013 ms.

### 2.7 Recommendation

- The consumer runner keeps `owned: Set<number>` per group from `rebalance_cb`; the healthcheck reports healthy when every group's set is non-empty.
- The runner computes the highest contiguous completed offset itself, calls `resolveOffset` only with that, commits `offset + 1`, and on a transient failure calls `pause()`, `seek()` to the first unfinished offset, and schedules `resume()` through `resumeLater` (2.4). It cancels a partition's timer when the partition is revoked and cancels all timers before `disconnect()`.
- Every batch's wall time is bounded, because the slowest in-flight batch holds up the member's fetches, seeks and rebalances. Use hard client-side PSP timeouts, and a per-batch deadline after which the runner starts no new work, waits for the work in flight (bounded by those timeouts), resolves the contiguous prefix and returns. A smaller `js.consumer.max.batch.size` for the payment group is the other lever. A batch's worst case is then the deadline plus the PSP timeout.
- `partitionsConsumedConcurrently` is for throughput only: equal to the partitions a member can own (3 with 2 replicas on 6 partitions). It does not isolate a slow partition.
- §6.4's "the main loop keeps polling, so `max.poll.interval.ms` is never exceeded" holds only while batches stay short: while a batch is in flight the member calls no `consume()` (source). With bounded batches the 300 s default is never approached.
- The relay uses the producer config from 2.2 verbatim; its send settles within `message.timeout.ms` as §5.4 requires.

### 3.4 Revalidation route handler

```ts
// app/%5Finternal/revalidate/route.ts  -> served at /_internal/revalidate
import { timingSafeEqual } from 'node:crypto';
import { revalidateTag } from 'next/cache';
import { z } from 'zod';

const Body = z.object({ tag: z.string().min(1).max(256) });

// Read at request time: route modules are evaluated during `next build` (page data collection), where no secret exists.
let secret: Buffer | undefined;
function revalidateSecret(): Buffer {
  if (secret) return secret;
  const value = process.env.REVALIDATE_SECRET;
  if (value === undefined || value.length < 32) throw new Error('REVALIDATE_SECRET must be at least 32 characters');
  secret = Buffer.from(value);
  return secret;
}

// timingSafeEqual throws on a length mismatch, so compare lengths first; the secret's length is not secret.
function authorized(header: string | null): boolean {
  if (header === null) return false;
  const expected = revalidateSecret();
  const given = Buffer.from(header);
  return given.length === expected.length && timingSafeEqual(given, expected);
}

export async function POST(request: Request) {
  if (!authorized(request.headers.get('x-revalidate-secret'))) return new Response(null, { status: 401 });
  const body = Body.safeParse(await request.json().catch(() => undefined));
  if (!body.success) return Response.json({ error: 'invalid body' }, { status: 400 });
  revalidateTag(body.data.tag, 'max');
  return Response.json({ revalidated: body.data.tag });
}
```

- With both `app/_internal/revalidate/route.ts` and `app/%5Finternal/revalidate/route.ts` present, the build listed one route, `/_internal/revalidate`, and requests were answered by the `%5F` file; `POST /%5Finternal/revalidate` returned 404.
- Against the standalone server with a 40-character secret (zod 4.6.5): no header, an empty header, a wrong secret of the same length and a wrong secret of another length → `401`; the right secret with a non-JSON body or `{"tag":""}` → `400`; the right secret with `{"tag":"drops"}` → `200`. (The spike's route also accepted an `expireNow` flag for the 3.6 checks.)
- **Build-time evaluation:** with `const secret = revalidateSecret()` at module scope and no `REVALIDATE_SECRET` in the build environment, `next build` failed: `Failed to collect configuration for /_internal/revalidate`, caused by the thrown error at module evaluation. The lazy version above built without the variable (design delta 13).
- In the repo, `packages/config` already declares `REVALIDATE_SECRET: secret(32)` in `RevalidateEnv`; parse it lazily in the same way rather than at import time.

### 3.8 Gotchas

- **`next build` rewrites `apps/web/tsconfig.json` unless it uses `extends`.**
  - The spike's own tsconfig (no `extends`, `module: esnext`) gained `allowJs: true`, `incremental: true` and a `.next/dev/types/**/*.ts` include, and `esModuleInterop: true` was forced ("mandatory").
  - The forced values are conditional (source: `next/dist/lib/typescript/writeConfigurationDefaults.js`, which reads the app's own file, not what it inherits). `esModuleInterop`, `moduleResolution` and `resolveJsonModule` are forced only when that file does not set `module: "preserve"`; `isolatedModules` only when it does not set `verbatimModuleSyntax: true`. With both set in the file, the build added only `allowJs`, `incremental` and the `.next/dev/types` include (verified).
  - A tsconfig with `extends` is never rewritten (source: the function returns early on `extends` or `references`). Verified: an `apps/web/tsconfig.json` extending a copy of the repo's `tsconfig.base.json` was byte-identical after `next build`. The build's TypeScript step still used it: a deliberate type error failed the build, and the spike app passed under the base's `module: Preserve`, `verbatimModuleSyntax` and `erasableSyntaxOnly`.
  - Recommended `apps/web/tsconfig.json`, which built unchanged:

    ```json
    {
      "extends": "../../tsconfig.base.json",
      "compilerOptions": {
        "lib": ["ES2023", "DOM", "DOM.Iterable"],
        "jsx": "react-jsx",
        "plugins": [{ "name": "next" }]
      },
      "include": ["next-env.d.ts", "**/*.ts", "**/*.tsx", ".next/types/**/*.ts", ".next/dev/types/**/*.ts"],
      "exclude": ["node_modules"]
    }
    ```

    Because Next does not touch an extending config, the `include` entries Next would otherwise add (`.next/types`, `.next/dev/types`) must be listed by hand, as above.
- Folders starting with `_` are private (design delta 1).
- `cookies()`/`headers()` inside a `'use cache'` scope fail, and the restriction follows the call stack (docs); session-dependent reads stay outside cached helpers and pass values in as arguments.
- The default `use cache` handler is in-memory per instance (docs), which matches §2's single `web` replica.

### 3.9 Recommendation

- Use the 3.2 config, the 3.3 page shape for `/` and `/p/[slug]`, the 3.4 route at `app/%5Finternal/revalidate/route.ts`, `export function proxy` in `apps/web/proxy.ts`, and the 3.8 `tsconfig.json`.
- For catalog pages, prefer `await io()` over `connection()`: both keep `api` out of the build (verified), and the docs say `connection()` also blocks prefetches while `io()` lets the cached part be prefetched. Use `connection()` only where a real request must be waited for. This is a one-word change to §8.1.
- `web` reads its runtime env (`REVALIDATE_SECRET`, `API_INTERNAL_URL`, the session key) lazily, never at module scope, so `next build` needs none of it.

### 4.2 Migrator

### 4.3 Custom migration: `orders_guard`

`drizzle-kit generate --custom --name orders_guard` writes an empty `NNNN_orders_guard.sql` plus a journal entry; a later `generate` (adding a column) produced the next number normally. The body that ran:

```sql
-- orders_guard: inserts only as RESERVED or REJECTED; updates only along the §4.4 edges;
-- terminal rows are immutable apart from redis_settled_at. Stored generated columns (total_cents) are still NULL in NEW
-- inside a BEFORE trigger, so they are left out of the comparison.
CREATE FUNCTION orders_guard() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    IF NEW.status NOT IN ('RESERVED', 'REJECTED') THEN
      RAISE EXCEPTION 'orders_guard: cannot insert an order as %', NEW.status
        USING ERRCODE = 'check_violation', CONSTRAINT = 'orders_guard';
    END IF;
    RETURN NEW;
  END IF;
  IF OLD.status NOT IN ('RESERVED', 'PENDING_PAYMENT') THEN
    IF (to_jsonb(NEW) - 'redis_settled_at' - 'total_cents') IS DISTINCT FROM (to_jsonb(OLD) - 'redis_settled_at' - 'total_cents') THEN
      RAISE EXCEPTION 'orders_guard: order % is terminal (%)', OLD.id, OLD.status
        USING ERRCODE = 'check_violation', CONSTRAINT = 'orders_guard';
    END IF;
  ELSIF NEW.status IS DISTINCT FROM OLD.status AND NOT (
       (OLD.status = 'RESERVED' AND NEW.status IN ('PENDING_PAYMENT', 'EXPIRED', 'CANCELLED'))
    OR (OLD.status = 'PENDING_PAYMENT' AND NEW.status IN ('PAID', 'PAYMENT_FAILED', 'EXPIRED', 'CANCELLED'))) THEN
    RAISE EXCEPTION 'orders_guard: illegal transition % -> %', OLD.status, NEW.status
      USING ERRCODE = 'check_violation', CONSTRAINT = 'orders_guard';
  END IF;
  RETURN NEW;
END
$$;
--> statement-breakpoint
CREATE TRIGGER orders_guard BEFORE INSERT OR UPDATE ON orders FOR EACH ROW EXECUTE FUNCTION orders_guard();
```

- The migrator split the file on `--> statement-breakpoint` and ran the dollar-quoted body as one statement.
- Results: insert as `PAID` → `23514`, `constraint = 'orders_guard'`; `RESERVED → PAID` → rejected; `RESERVED → PENDING_PAYMENT → EXPIRED` → ok; setting `redis_settled_at` on the `EXPIRED` row → ok; changing `qty` on it → rejected.
- **Without** excluding `total_cents`, setting `redis_settled_at` on a terminal row was rejected, because `NEW.total_cents` is `NULL` in a BEFORE trigger (design delta 8).
- `RAISE ... USING CONSTRAINT = 'orders_guard'` surfaces as `DatabaseError.constraint`, so the API can map the trigger like a named constraint.

### 4.4 Transactions, `FOR UPDATE SKIP LOCKED`, hand-written SQL

```ts

//                         order by "outbox"."id" asc limit $1 for update skip locked

    .orderBy(asc(outbox.id)).limit(500).for('update', { skipLocked: true });

// Hand-written form with typed rows; a JS array bound as ONE parameter needs sql.param().
await db.transaction(async (tx) => {
  const r = await tx.execute<{ id: string; partition_key: string; payload: unknown }>(sql`
    SELECT id, partition_key, payload FROM outbox
    WHERE published_at IS NULL ORDER BY id LIMIT 500 FOR UPDATE SKIP LOCKED`);
  const ids = r.rows.map((row) => row.id);
  await tx.execute(sql`UPDATE outbox SET published_at = now() WHERE id = ANY(${sql.param(ids)}::bigint[])`);
});

// Table references interpolate as identifiers inside the template:
await db.execute<{ id: string; qty: number; from_status: 'RESERVED' | 'PENDING_PAYMENT' }>(sql`
  WITH due AS (SELECT id, status AS from_status FROM ${orders}
               WHERE status IN ('RESERVED','PENDING_PAYMENT') AND expires_at < now()
               ORDER BY expires_at LIMIT 200 FOR UPDATE SKIP LOCKED)
  UPDATE ${orders} o SET status = 'EXPIRED', closed_at = now(), version = version + 1, updated_at = now()
  FROM due WHERE o.id = due.id
  RETURNING o.id, o.qty, due.from_status`);
```

- Two concurrent transactions each took 4 rows with `SKIP LOCKED` and got disjoint sets (`[21..24]` and `["25".."28"]`).
- ``sql`SELECT ${[1, 2, 3]}` `` renders as `SELECT ($1, $2, $3)`, and `IN ${[1, 2, 3]}` as `IN ($1, $2, $3)`. `= ANY(${sql.param(ids)}::bigint[])` binds one array and updated the 4 rows.
- ``sql<number>`count(*)`.mapWith(Number)`` in a builder select returned a `number`; without `mapWith`, ``sql<string>`max(id)` `` returned the string `"30"`. The generic is a type claim only.
- `db.transaction(fn, { isolationLevel: 'repeatable read', accessMode: 'read only' })` ran at `repeatable read`.
- `tx.rollback()` throws `TransactionRollbackError` out of `db.transaction`; the row was unchanged.
- Query errors are wrapped: `err instanceof DrizzleQueryError` (message `Failed query: ...`), with the `pg.DatabaseError` (`code`, `constraint`) as `err.cause`. Inside `db.transaction`, an error that kills the connection is replaced by the failed `ROLLBACK`'s error (4.6).

### 4.6 Pool session settings and connection-killing errors

```ts
const pool = new pg.Pool({ connectionString: env.DATABASE_URL, max: 10, options: '-c statement_timeout=2s -c transaction_timeout=5s' });
// A checked-out client that loses its session (transaction_timeout is FATAL) emits 'error' on itself, not on the pool.
pool.on('connect', (client) => client.on('error', (err) => logger.warn({ err }, 'pg client error')));
pool.on('error', (err) => logger.warn({ err }, 'idle pg client error'));
```

- `options` is sent in the startup packet: `current_setting('statement_timeout')` = `2s` and `transaction_timeout` = `3s` (the spike's value) on every pooled connection, before its first query. The URL form `?options=-c%20transaction_timeout%3D5s` also worked.
- `statement_timeout`: `pg_sleep(2.5)` failed with `57014` `canceling statement due to statement timeout`; the connection survived.
- **Without the per-client listener the process crashed** with an unhandled `'error'` event (`Connection terminated unexpectedly`) on the `Client`. With it, the client's `'error'` events carried `25P04 terminating connection due to transaction timeout` and `Connection terminated unexpectedly`, and the pool discarded the dead client and served the next query.

**What the caller sees when `transaction_timeout` (3 s) fires** (`pg` 8.23.1, `postgres:17.11`):

| Case | Error |
|---|---|
| Raw `pg`, statement running (simple or parameterized query; two `pg_sleep(1.8)`) | `DatabaseError` `code 25P04`, `severity FATAL`, `terminating connection due to transaction timeout`, after 3,001–3,002 ms. |
| Raw `pg`, session idle in the transaction, then the next query | `Error: Client has encountered a connection error and is not queryable`, no code. The `25P04` arrived only through the client's `'error'` event. |
| `db.transaction`, statement running: error inside the callback | `DrizzleQueryError` `Failed query: SELECT pg_sleep($1)`, cause `25P04` FATAL. |
| `db.transaction`, statement running: error thrown to the caller | `DrizzleQueryError` `Failed query: rollback`, cause `Connection terminated unexpectedly`. The `25P04` is lost. |
| `db.transaction`, idle, then the next query | Inside: `Failed query: SELECT 2`, cause `... not queryable`. Thrown: `Failed query: rollback`, cause `... not queryable`. |

(source) `drizzle-orm/node-postgres/session.js` (`transaction`): ``catch (error) { await tx.execute(sql`rollback`); throw error; }``. On a dead connection the `ROLLBACK` itself rejects, and that rejection escapes instead of `error`. This applies to every connection-killing error inside any Drizzle transaction, not only `transaction_timeout`.

A wrapper that keeps the original error (ran in the same script):

```ts
export async function transaction<T>(db: Db, fn: (tx: Tx) => Promise<T>): Promise<T> {
  let failure: { error: unknown } | undefined;
  try {
    return await db.transaction(async (tx) => {
      try {
        return await fn(tx);
      } catch (error) {
        failure = { error };
        throw error;
      }
    });
  } catch (error) {
    // Drizzle's ROLLBACK failed too (the connection is gone) and its error replaced the callback's: keep the original.
    if (failure === undefined || error === failure.error) throw error;
    if (failure.error instanceof Error) Object.assign(failure.error, { rollbackError: error });
    throw failure.error;
  }
}
```

- With the wrapper, both timeout cases threw the callback's error (`Failed query: SELECT pg_sleep($1)` with its `25P04` cause, or `Failed query: SELECT 2` with `... not queryable`), with the `Failed query: rollback` error attached as `rollbackError`.
- An error thrown by the callback on a live connection (the `ROLLBACK` succeeds) came out unchanged.

### 4.7 Recommendation

- Schema per 4.1, one `bytea` custom type in `packages/db`, explicit names for every constraint the invariant test checks.
- Guarantee-carrying SQL per 4.4 through `sql`, with each statement's row type declared at the call and parsed (Zod or explicit mapping) where timestamps or bigints are read.
- Pools per 4.6: api `statement_timeout=2s, transaction_timeout=5s`; relay `idle_in_transaction_session_timeout=30s, transaction_timeout=20s` through the same `options` mechanism; the migrate job without timeouts.
- `packages/db` exports the 4.6 `transaction()` wrapper, and all code uses it instead of `db.transaction`. Logs carry the original error, never `Failed query: rollback`.
- `packages/db` also exports the transient-error classifier that maps to 503 `RETRY` in `api` and to pause-and-retry in consumers. It walks the `cause` chain and treats as transient: SQLSTATE `25P04` (observed), any `DatabaseError` with `severity FATAL`, and `pg`'s code-less connection errors `Connection terminated unexpectedly` and `Client has encountered a connection error and is not queryable` (both observed).
- `orders_guard` per 4.3 as the custom migration right after the initial one.
- One agent owns `packages/db/drizzle/`; never edit an applied migration; CI fails if `drizzle-kit generate` produces a diff.
